Contributing

Bibliofeed is a small, open-source project: a static web app with no framework and a Supabase database behind it. The code is at github.com/SebastienHiggs/bibliofeed under the MIT licence. Bug reports, fixes and careful improvements are welcome.

What it's made of

  • web/: the site. Plain HTML, CSS and JavaScript modules, served as static files by Cloudflare. js/app.js is the feed and routing, js/post.js a post, js/activity.js your likes, saves and comments, js/backend.js the only module that talks to Supabase.
  • data/bsb/: the Berean Standard Bible, one JSON file per book, committed so builds need no network.
  • supabase/: the database as migrations (five tables, a few functions, and the row-level security rules that decide who may see what), its tests, and the local stack's settings.
  • docs/supabase-backend/README.md: the plan behind the accounts and friends features, the decisions taken and why, and a log of what was verified. Read it before changing the backend or anything that touches it.

Running the app

You need Node.js 22 or later. Signed out, the app has no backend to run:

cd web
npm install     # once
npm start       # http://localhost:8080

Running the backend locally

Accounts, friends and syncing use Supabase. Contributors run their own copy of it, never the live one: the hosted project belongs to the site's owner, and nothing in the repository gives anyone else access to it (the project URL and key in js/config.js are public by design; the database's access rules are the protection). With Docker running:

npx supabase start            # at the repository root; prints the local URL and key

Put the API URL and publishable key it prints into web/js/config.local.js, which is ignored by git and served in place of config.js while developing:

export const SUPABASE_URL = 'http://127.0.0.1:54341';
export const SUPABASE_KEY = 'sb_publishable_…';
export const TURNSTILE_SITE_KEY = '';

Sign-in codes arrive in the local mail catcher at http://127.0.0.1:54344. The sign-in form's bot check is off locally; supabase/config.toml explains how to try it with Cloudflare's test keys. npx supabase db reset gives you a clean database; npx supabase stop stops the stack.

Tests

  • Browser tests: npm test in web/ (Playwright; run npx playwright install chromium once) walks through signing in, syncing, friends, importing and deleting an account against the local stack.
  • Access-rule tests: sh supabase/tests/run.sh resets the local database and checks that every rule does what the plan says. Change a policy, add a check.

Both run on every pull request.

How changes are reviewed

  • Work on a branch and open a pull request into main; nothing is pushed to main directly. The owner reviews every pull request, and the tests must pass.
  • Keep changes small and focused, with commit messages that say why. Say what you checked in the browser or the database; the project's habit is to verify each piece against the local stack.
  • The project prefers simple and maintainable over feature-rich: no server code, no analytics, no placeholders for features that don't exist yet. Store only what the app needs, and never anything that would identify people to each other beyond their username and display name.
  • Changes to the database go in a new migration under supabase/migrations/, with the plan document updated to match. Changes to what is stored about people also need the about page updated.
  • Not sure whether something fits? Open an issue first; it saves everyone time.
